# Workshop: Kip and Truck in one place (draft 1, 2026-11-02)

One standalone page, `/kip/Workshop.html`, with a tab per bench. It exists so the Kip configurator and the mechanical truck can be tested together, and so their shared pieces (rig, menu, print view) can be unified step by step, before any of it moves into the game.

## Name

**Workshop.** "Factory" is already the game's stage (`?tab=factory` in `src/App.tsx`, `ToyCustomizer` "World Factory", the Factory missions), and this is meant to land there, so a second Factory would make "merge Factory into Factory" ambiguous. The only other "workshop" is the old worktree/branch `worktree-workshop` (the Describe tab), which is finished and on disk.

## Stages

| Stage | What | State |
|---|---|---|
| 1 | Shell (`workshop.js`) hosting each bench as a page in an iframe, one at a time. Kip-Demo.html and Truck-Mockup.html untouched. | built, `npm run e2e:workshop` |
| 2 | Turn the generated `kip-rig.js` (cut out of Kip-Demo.html by `parts/kip/sync_kip_rig.py`) into a real module that both benches import; delete the sync script. Needs Kip-Demo.html and Truck-Mockup.html edited. | built, `npm run e2e:workshop` |
| 3 | Print view takes a parts provider instead of reading Kip's scene state (below). | not started |
| 4 | Benches become modules mounted in one scene, one menu, one print view. Then mount in the game. | not started |

Stage 1 deliberately embeds whole pages. What it buys: one place to open both, a tested tab and URL contract, no edits to files other sessions own, a hidden bench is unloaded (its WebGL context is freed), and the host boundary the game needs (`mountWorkshop(el, { urlSync: false })`, no globals, does not touch the host's URL or title). What it does not buy: the two benches still have their own menus and print views; the shell cannot yet carry a model from one bench to the other.

## Contract the shell keeps (tested in `tests/workshop.test.ts` and `scripts/e2e-workshop.mjs`)

- `?bench=<id>` picks the bench; every other query param is forwarded to it on that load only (`?bench=kip&vehicle=truck`, `?bench=truck&driver=snap&head=fox`). Picking a tab opens the bench clean.
- A tab pick pushes history; Back and Forward step between shell states (a fresh iframe element per switch, so the browser never steps into a bench's private history).
- A bench that navigates itself (the Truck page's "Kip Viewer" link) is followed: tab, title and address bar change, nothing reloads.
- The shell knows no bench internals (no `kipMenu`, `__KIP_READY__`; a test greps for it). A new bench is one entry in `DEFAULT_BENCHES` plus a page.
- Iframe permissions: `camera; fullscreen; clipboard-write` (the selfie uses the camera).

## Print view for the Truck (stage 3), from reading the code

Checked:
- `resolveSceneBom(state, opts)` in `kip-print-bom.js` takes Kip's scene state (edition, vehicle, head, prop, colours). Its part-to-STL tables are hard-coded and name the `veh_*` cover, chassis and wheel parts. It names none of the Truck's ids (`kit_*`, `pro_*`, `mom_*`, `mech_*`: 0 hits).
- All 42 part ids the Truck loads have entries in `public/kip/partspec-validation.json`: 32 pass, 9 pass with warnings (kit_keel_base, both steer knuckles, mom_bellows_base and others), 1 pass with settings (shaft_tu03). The plate tiers therefore have data to work from.
- The Truck draws assembly-pose copies (`public/kip/partspec/mockup/`, regenerated by `sync_truck_kip.py`); the print view needs the print-frame STLs (`_S` / `_P`) the validation index names. A part can print rotated relative to its assembly pose (`print.rotation_deg` in the manifest; four of the Describe tab's 30 parts do). Which Truck parts do was not checked.

So the extension is a provider interface, `getParts() -> [{ id, colour, count }]` plus how to find each part's print STL, that Kip's resolver implements today and the Truck implements next; colour and plate planning stay as they are.

Not checked (do before building stage 3): whether the 9 warning parts need a different print setting on the Ender-3 Pro profile; how a moving assembly should be laid out (fit setting snug/standard/easy and free-versus-friction pins from the calibration kit; layer direction for axles and pins); whether the sprue/kit-card layout suits a mechanism.
