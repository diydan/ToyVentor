# Describe & build: recipe contract (v1)

A recipe is an ordered list of catalog parts and how each one mates to an earlier one. It is the only thing that crosses the boundary between the
text description, the (optional) language-model endpoint, the validator and the 3D viewer. Poses are never written by a model: they are derived from the
mates by the real assembly code (`toyventor_assembly.attach` and `place_on_axis`) and come back with the recipe once the real validator has passed it.

Files (all under `parts/kip/viewer/`):

| file | what it is |
|---|---|
| `kip-describe-recipes.json` | curated parts + ten fixture recipes with reference poses; also the offline recipe book |
| `kip-describe-parts.json` | GENERATED by `tools/build_parts_data.py` (`--check` for staleness): the 30 parts' connectors and the fit-matrix groups |
| `kip-describe.js` | the matcher: endpoint, then recipe book, then closest |
| `kip-describe-validate.js` | the browser-side validator (checks 1 to 4 below) and plain-language wording for validator errors |
| `tools/describe-endpoint.mjs` | local model endpoint: asks the model, checks the answer with the real validator, retries once with the reasons |
| `tools/validate_worker.py` | the persistent worker that runs the real validator (needs the PartSpec virtual environment) |
| `tools/check_recipes.py` | fixtures against the real validator, one shot; writes the reference poses (`--write`) |
| `tools/check_validate.mjs`, `tools/check_describe.mjs` | fast self-checks (no key, no Python): validator wording and rules; matcher and endpoint with a mock model and a fake checker |
| `tools/check_worker.mjs` | slow integration check of the real worker: fixtures pass with exactly their poses, known-bad recipes are refused |
| `kip-describe-view.js` | the exploded view and the build animation: pose maths, the two plans and the build timeline (pure, Node-testable) plus the three.js drawing of a recipe |

| `public/kip/partspec/describe/*.stl` | the 30 parts in ASSEMBLY orientation, written by `tools/export_describe_stls.py` (`--check` for staleness); 13 MB in all, a recipe loads only its own parts |

## Recipe

```json
{
  "title": "Roadster",
  "description": "a race car",
  "steps": [ { "id": "car", "part": "veh_car_chassis" },
             { "id": "hood", "part": "veh_car_hood_cover",
               "mate": { "conn": "under_sockets", "host": "car", "hostConn": "hood_studs" } } ]
}
```

| field | meaning |
|---|---|
| `title` | short name shown in the tab (optional) |
| `description` | the user's text, echoed back (optional) |
| `steps` | build order. Step 0 is the base and has no `mate`; every later step has one |

## Step

| field | meaning |
|---|---|
| `id` | unique within the recipe; letters, digits, `_` |
| `part` | catalog part id, must be on the curated list for this task |
| `mate` | how this part joins its host (absent only on step 0) |

## Mate

`conn` is the connector on **this** part, `hostConn` the connector on the host, `host` the id of an **earlier** step. What else is allowed depends on the
kind of connector, which the validator reads from the part manifest, so a recipe never states it:

| connector kind | extra fields | meaning |
|---|---|---|
| stud grid / socket grid (stacking) | `hostCell` `[i, j]`, `cell` `[i, j]`, `rot` 0..3 | which stud cell on the host meets which cell on this part (default `[0, 0]`), and quarter turns relative to the host (default 0) |
| pin / bore (an axle, shaft, hub or face slot on an axis) | `along`, `hostCell` | where the pin sits along the bore (below) |

`along` is a signed millimetre offset of this part's connector origin from the host connector's origin, along the axis. A model must not do arithmetic, so
it may use an anchor instead of a number. With `h` = the host connector's span and `c` = this connector's span (a pin's `length_mm`, a bore's or hub's
`depth_mm`):

| anchor | offset |
|---|---|
| `start` | `0` |
| `center` (default) | `(h - c) / 2` |
| `end` | `h - c` |

Examples: an axle centred in a chassis bore is `center`; two wheels on one axle are `start` and `end`; a face plate seated in a head's face slot is `start`.

## Legal means

A recipe is accepted only if all of these hold. Checks 1 to 4 need nothing but `kip-describe-parts.json` and run in the browser
(`kip-describe-validate.js`) and in the endpoint. Check 5 needs geometry and runs only in the endpoint's worker; the fixtures are held to all five.

1. **structure**: unique ids; hosts precede their step; only step 0 lacks a mate; fields match the connector kind; `rot` is 0..3; cells are inside the grid.
2. **allowed**: every `part` is in `allowedIds` of the request.
3. **connectors exist** on both parts.
4. **fit matrix**: (male connector, female connector) is a pair in `fit_matrix.json` with `as_designed` and `in_window` true.
5. **validator**: `toyventor_assembly.validate` reports no errors (a mate that cannot be seated, floating parts, size classes, exact collisions).

**Why 5 cannot be skipped.** The fit matrix says two connectors fit each other by size and tolerance. It says nothing about whether the finished pieces
occupy the same space. Among the 30 curated parts it has only four connector groups: every stud connector mates with every socket connector, and every
pin with every bore (the grouped table the endpoint puts in its prompt shows this). A hat plugged into the arms' studs is a "legal" pair and only check 5
reports the 1180 mm3 collision. A live model recipe for "a scooter with Kip riding it" used the 62.5 mm axle shaft instead of the racer axle (also a
legal pair); its wheels overlapped the scooter frame by about 6,600 mm3 each. Checks 1 to 4 catch typos and invented parts, not bad design.

**Where the overlap check lives.** Not in the browser: an exact check needs the part meshes, and the shipped viewer files cover only some of the 30
parts. The endpoint runs check 5 and says so: a reply carries `validated: true` and the poses of every step, or it carries no steps. The page treats
a model recipe without `validated: true` plus usable poses as unchecked (confidence `low`, a warning in the note). The recipe book is always validated.

Validation failures are `{ step, code, message, suggestion?, detail? }` (`ok: false` plus a list of them from `validateRecipe`); `message` is plain
language for a grown-up ("The cowboy hat's under sockets cannot plug into the kid head's face slot"), `suggestion` names a legal alternative when one
exists, `detail` is the raw validator text (kept for logs and the model's retry prompt, not shown to a child). `code` is one of
- browser rules: `no_steps`, `duplicate_id`, `not_allowed`, `unknown_part`, `unknown_host`, `host_after_step`, `missing_mate`, `unexpected_mate`,
  `unknown_connector`, `kind_mismatch`, `bad_field`, `cell_out_of_range`, `no_legal_pair`;
- real validator: `collision`, `floating`, `cannot_place`, `profile_mismatch`, `size_mismatch`, `misaligned`, `unsupported_pose`, `structure`
  (the worker's own copy of checks 1 to 4), plus `validator_down` / `validator_timeout` when the worker cannot answer.

## Model endpoint (optional, provider-agnostic)

The viewer is static. When the user configures an endpoint URL (and, if it needs one, a key held in session storage only), the matcher POSTs JSON:

```json
{ "contract": 1, "description": "Kip with a cowboy hat", "allowedIds": ["veh_car_chassis", "..."] }
```

and accepts exactly one of these as the 200 response body:

```json
{ "steps": [ ... ], "title": "optional", "note": "optional", "validated": true, "poses": { "car": { "x": 0, "y": 0, "z": 0, "rot": 0 } } }
{ "clarifyingQuestion": "Do you want a car or a truck?" }
{ "error": "plain-language reason" }
```

`validated: true` is the endpoint's statement that the real validator passed these steps; `poses` then has one entry per step id (mm in the validator's
frame, `rot` in quarter turns about Z, optional `tilt` in degrees), ready to draw. An endpoint with no validator may send plain `{ steps }`; the page
then marks the result unchecked.

The endpoint owns the prompt and the model; the page sends no catalog text. The page still checks whatever comes back (the browser rules, checks 1 to 4,
when it has loaded `kip-describe-parts.json`) before it renders, so an illegal mate never renders even from an endpoint that skips check 5. Anything
other than a 200 with one of the three bodies is treated as "endpoint unavailable".

### Running the local endpoint

The page holds no key. The key stays in this process, which reads the repo's `.dev.vars` (the nearest one up the directory tree, so it works from a git
worktree) and listens on loopback only:

```
node parts/kip/viewer/tools/describe-endpoint.mjs --model <model id>        # port 8788, POST /describe, GET /health
```

Key: `DESCRIBE_API_KEY`, else `MODEL_API_KEY`, else any variable ending in `MODEL_API_KEY`. URL: `DESCRIBE_API_URL`, else any variable ending in
`MODEL_API_URL`. The model id has no default (the repo names no provider): pass `--model` or set `DESCRIBE_MODEL`. Other flags: `--port`, `--env-file`,
`--effort low|none`. The wire format is `POST {url}/responses` with `{model, input}` and a bearer key, reading `output_text` or `output[].content[].text`.

What it enforces: loopback origins only (CORS), 16 KB body, description 1 to 300 characters, at most 60 allowed ids of the form `[a-z0-9_]`, 20 requests a
minute, 20 s for each model call (one retry without the reasoning parameter if the model rejects it) and 45 s for the whole answer. It answers 200 with
exactly one of the three bodies above (upstream failures become `{ "error": ... }`); malformed requests get 400, 413, 415 or 429. Only whitelisted recipe
fields leave the process: the model's raw text, the key and the upstream URL never do, links in `title` or `note` are dropped, and log lines carry status
and timing only.

**Check and retry.** Each model recipe goes through the browser rules and then the real validator (`tools/validate_worker.py`, started with the endpoint;
the PartSpec virtual environment is found by walking up for `parts/partspec/.venv`, or `--python` / `DESCRIBE_PYTHON`; `--validator off` skips it).
A recipe that fails is sent back to the model once (`--retries`, default 1) together with its own rejected answer and the reasons, both the plain message
and the raw detail. Steps leave the endpoint only when they pass; if they still fail the reply is `{ "error": "I could not make a build that fits
together from that. <the first reasons>" }`. The worker builds every curated part first, which takes a minute or two (`GET /health` reports
`validator: "warming" | "ready" | "down" | "off"`); a request that arrives during the warm-up gets a quick error and never reaches the model.

The prompt is built from the real data: the allowed parts with their connectors and grids; the fit-matrix pairs between exactly those parts (grouped);
the connections used in tested builds (every mate of the fixture recipes, with their cells and `along` values, plus every edge of the hand-written
`valid_*` assemblies), which it tells the model to prefer; the placement rules in prose; and the three tested builds closest to the description as
examples (the recipe book's own ranking, topped up with defaults). The tested connections matter because the matrix says almost everything fits
everything: without them a live model put a scooter rider on the wrong connector and used the wrong axle, and the fit checker refused it twice; with
them, six live descriptions went 4 for 4 on the first model call for builds that exist, and the two that cannot be built were refused plainly.

## The app's own route (`/api/describe`)

With the Settings address empty, the tab POSTs the same body to `/api/describe` (`worker/describe.ts`, `defaultEndpoint` in `mountDescribe`; pass `''` to turn it off). The Worker asks Muse to **choose** one of the ten ready builds in `kip-describe-recipes.json` and replies with the third body above (`steps`, `title`, `note`, `validated: true`, that build's reference `poses`), or `{ "clarifyingQuestion": "..." }` when the words are unclear. It never invents steps, because poses must come from the real validator, which cannot run in a Worker. Any failure is a non-200, and the tab then falls back quietly (`describe(..., { quiet: true })` leaves out the "endpoint could not be used" aside; a typed address always wins and is never quiet). The badge reads "Picked by Muse from the checked builds".

## Matcher result (step 2)

`describe(description, { endpoint, book, parts })` in `kip-describe.js` always resolves to `{ steps, title, source, confidence, note, validated, poses? }` with
non-empty `steps`: `source` is `"model"`, `"recipe-book"` (keyword match against the fixtures' `keywords`) or `"closest"` (nearest recipe when nothing
matches), `confidence` is `"high"`, `"medium"` or `"low"` (how well the build matches the words, never whether it fits), `note` says in one or two plain
sentences what happened, and `validated` says the real validator passed the steps, in which case `poses` are their poses. It never throws on a bad
endpoint. Pass `parts` (the indexed `kip-describe-parts.json`) to run the browser rules on model recipes too.

- Endpoint steps come back as `source: "model"`. With `validated: true` and usable poses from the endpoint: `confidence: "medium"`. Otherwise
  `validated: false`, `confidence: "low"` and the note ends "This recipe was not checked for fit." (A claim of `validated: true` without poses that
  cover exactly the steps is not believed.)
- With `parts` supplied, a model recipe that breaks the browser rules is dropped and the recipe book answers, the note saying why.
- Recipe book answers are always `validated: true` with the fixture's reference poses.
- An endpoint question comes back as the recipe book's best guess plus `clarifyingQuestion`, so the tab can show a build and ask at once.
- An endpoint error, a non-200, a timeout, a network failure or an unusable reply (bad shape, a part not on the list) falls back to the recipe book and
  the note says why.
- Recipe book scoring: a keyword found as a whole phrase scores its word count, saying a recipe's own description scores 10; 3 or more (or an exact
  description) is `high`, 1 to 2 is `medium`, and no keyword hit is `closest`/`low`, chosen by content-word overlap (filler such as "a" and "with" is
  ignored; with no overlap at all the first recipe is the starting point).
- The shape check (`stepsShapeProblem`) only rejects malformed recipes. Whether the mates are legal and the parts do not collide is the validators' job.

## Exploded view (step 4)

**Drawing a recipe.** `createDescribeView(...).show(result)` needs `result.steps` and `result.poses` (a `validated` result from `describe()`); a recipe
without poses is never drawn. Each step is one mesh of `public/kip/partspec/describe/<part>.stl` (assembly orientation, so no per-part fix-ups; the shipped
print-orientation files are not used). A pose is applied as tilt, then quarter turns about Z, then translation: `R = Rz * Ry * Rx`, in three.js a mesh with
`rotation.order = 'ZYX'` and `rotation.set(tiltX, tiltY, rot * 90 deg)`. The parts live in one group turned by -90 degrees about X (CAD Z-up to three.js
Y-up). `tools/check_explode.mjs` holds this to the validator: the box of every posed part equals the box of the validator's own placed geometry
(`reference.boxes` in the fixtures) to under 0.001 mm on all 10 fixtures, 39 of whose parts are turned or tilted.

**The plan.** `explodePlan` decides where each part goes at full spread, in build order. Each part tries the six axis directions and keeps the shortest
move that leaves at least 8 mm to every part already placed and does not sweep through a part it was not touching; it inherits its host's move, so it
travels with the host until it separates. A stacked part prefers straight up and a part on an axis prefers its own axis, each only if it costs no more
than 8 mm over the best alternative. The result is axle-and-wheel assemblies that drop out underneath with the wheels sliding outward, hats and heads
lifting as a stack, and a face plate leaving by the front. All boxes are axis-aligned boxes of the posed parts, so "no two boxes touch at full spread"
proves the parts do not interpenetrate. The slider is linear: a part sits at `pose + t * offset`, `t` from 0 (assembled) to 1. On the ten fixtures the
largest single move is 83 mm (a tall figure with hair and a hat). The gap was 3 mm at first; a render showed that reads as "almost assembled", so it is 8 mm.

**The tab.** `mountDescribe({ THREE, STLLoader, mergeVertices, toCreasedNormals, scene, camera, controls, setCharacterVisible })` adds a toggle button and a
panel: a text box, the ten sample descriptions as buttons, a status line with a badge (source, and whether the recipe is checked for fit), the exploded-view
slider, the step list (hover or focus highlights the part), and a Settings section for the endpoint address (kept in session storage; the page never
holds a key). While the panel is open `setCharacterVisible(false)` hides the host's own character. Keyboard shortcuts of the host do not fire while the
focus is in the panel.

## Build animation (step 5)

**Timeline.** A build has progress `p` from 0 (nothing seated) to `n` (finished), one unit per step. `buildFrame(p, n)` gives each step `{ visible, away,
alpha }`: step `i` owns the slot `p` in `(i, i + 1]`. It appears at the start of its slot, slides in (`away` falls from 1 to 0, with an ease-out, while it
fades in) for the first three quarters of the slot, then sits seated for the last quarter; earlier steps are seated and later ones hidden, so **at most
one part is ever moving** and the parts arrive strictly in recipe order. At `p = n` every part is opaque and exactly at its validated pose. With
`prefers-reduced-motion` a part simply appears seated, with no travel and no fade. A step takes 1100 ms by default (`stepMs`).

**Where a part comes in from.** The exploded-view plan cannot be reused, because it positions parts relative to the other parts' EXPLODED places while a
playing build has the earlier parts SEATED. So `explodePlan` also returns `approach[stepId]`, a second plan computed against the seated boxes: the part
starts at `pose + approach` (at least 30 mm out, with 4 mm clear of every seated part), slides to its pose, never sweeps through a seated part it is not
touching, and never cuts deeper into one it is touching than its seat does (a wheel may leave the hub's neighbour, not pass through the chassis).
`approachProblems(plan)` checks all of that; on the ten fixtures every part has a clear way in. Axles come in from underneath, wheels from the outside,
hats and heads from above.

**Controls.** Below the badge: Play build (Pause while playing, Resume when paused part-way), Back (remove the last part, instantly), Next (play the next
step in and stop), Replay (from nothing), and a progress line ("Step 3 of 10: Spoiler on the car chassis", "Built: all 10 parts are seated"). The step in
progress is highlighted in the list. A newly drawn recipe is shown finished; Play build on a finished build starts it over. The exploded-view slider is
for a finished build: it is locked while a build plays or is part-way, and returns to 0 when a build starts. Closing the panel pauses a playing build.
Tab API for hosts and tests: `play()`, `pause()`, `stepForward()`, `stepBack()`, `replay()`, `setBuildProgress(x)`, `progress`, `playing`.

**Host hook (applied in `Kip-Demo.html`).** After the module imports, `import { mountDescribe } from '/kip/kip-describe-tab.js?v=10.0';`, and next
to `mountPrintView(...)`:

```js
const describeTab = mountDescribe({
  THREE, STLLoader, mergeVertices, toCreasedNormals, scene, camera, controls,
  setCharacterVisible: on => { if (kip) kip.mover.visible = on; originRing.visible = on; },
});
window.kipDescribe = describeTab;
```

(`kip` is only set once `init()` has run, hence the guard.) `scripts/build-kip.ts` copies the six page files into `public/kip/` (explicit
`copyFileSync` entries, because `tests/kip-menu.test.ts` looks for the literal text `viewer/<file>.js` for every module the demo imports), and
`tests/kip.test.ts` brand-scans them. `tools/e2e_describe_host.mjs` tests the tab inside the real page (`E2E_SLOW` stretches its waits on a starved machine).

**What the real page taught.** Three things the development harness could not show, all fixed in `kip-describe-tab.js` and held by the host test:
- *Camera.* Opening the tab re-aims the host camera at the drawing, so it remembers the camera (position and orbit target) on open and restores it exactly on
  close; reopening re-aims at the existing drawing.
- *Host CSS leaks in.* Kip-Demo styles every `button` with `transition: all 0.12s` and `white-space: nowrap`, which made the toggle slide whenever the layout
  changed and kept long example chips on one line. The tab now sets `transition: none` on its toggle and panel and lets the chips wrap.
- *Sharing the screen.* The open panel starts 64 px down so it clears the host's top bar and leaves room for its toggle; at 900 px wide or less the toggle
  rises 52 px to clear the version strip, and at 640 px or less the open panel is a bottom sheet (its Close button and Escape dismiss it). The host's
  hide-UI key (H) adds `clean-ui` to the body and the tab hides with it. The host's single-key shortcuts (E, H, B) sit on `window` in the bubble phase with no
  input check, so the panel stops key events at its own root, exactly as the host's own menu panel does.

## Keys, settings and the public copies (step 6)

**Keys.** The plan had the page keep a key in session storage. It does not: the user's key lives in `.dev.vars` and is read by the local endpoint
(`tools/describe-endpoint.mjs`), so the page has no key to keep, nothing secret can reach the repo or a request from the page, and the browser test
asserts that a request carries no credentials. The only thing the page stores is the endpoint address, in `sessionStorage`, for the tab's lifetime; the
Settings box says what is sent (the description and the part names, to that address only), what is stored, and how to start the endpoint.

**Public copies.** The page is served from `public/kip/`, the sources are in `parts/kip/viewer/`, and the six page files must be byte-identical in both
(the Truck-Mockup pattern): `kip-describe.js`, `kip-describe-validate.js`, `kip-describe-view.js`, `kip-describe-tab.js`, `kip-describe-recipes.json`,
`kip-describe-parts.json`. `node parts/kip/viewer/tools/sync_public.mjs` makes them so and `--check` proves it (exit 1 on a missing or differing copy). The
30 STLs are written straight into `public/kip/partspec/describe/` by `tools/export_describe_stls.py` (`--check` for staleness). `E2E_PUBLIC_ONLY=1` runs
the whole browser test with only the public copies served, so a file missing from `public/kip/` fails it. Once `scripts/build-kip.ts` lists the six files,
`npm run build:kip` does the same copy and `sync_public.mjs --check` stays as a double check.

## Fixture file

`kip-describe-recipes.json` holds `allowedParts` (exactly 30, each `{ id, category, label }`) and `recipes` (each `{ id, description, title, keywords, steps, reference }`).
`reference` is written by the checker from the real validator and is not hand-edited:

```json
"reference": { "poses": { "car": { "x": 0, "y": 0, "z": 0, "rot": 0 } }, "boxes": { "car": [-29, -62.3, 0, 29, 62.4, 25.3] }, "validator": { "ok": true, "errors": 0, "warnings": 0, "edges": 9 } }
```

`boxes` are the world bounding boxes `[minx, miny, minz, maxx, maxy, maxz]` of the validator's own placed geometry; they are the ground truth the view's pose maths is tested against.

Poses are in millimetres in the validator's frame (X right, Y toward the back, Z up), `rot` in quarter turns about Z, and `tilt` (degrees, only for
parts that sit on an axis) is applied before `rot`. The page draws these poses as they are (the recipe book's come from the fixtures, a model recipe's from
the endpoint), so it needs no mate-to-pose maths of its own; `tools/check_worker.mjs` proves the worker reproduces them exactly.

Check, or refresh the reference poses after a deliberate change (needs the PartSpec virtual environment; read-only for `parts/partspec`):

```
parts/partspec/.venv/bin/python parts/kip/viewer/tools/check_recipes.py
parts/partspec/.venv/bin/python parts/kip/viewer/tools/check_recipes.py --write
```
